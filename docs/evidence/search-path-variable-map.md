# Search-path variable map — 2026-08-26

Every variable a SERVED recall reads, with the `file:line` where its value is actually
consumed, whether it LIMITS (raising it admits more) or ENABLES (turns a behaviour on),
what bounds it, and whether it is inert under the shipped configuration.

Produced by four parallel readers over the four path segments, followed by an adversarial
pass over every INERT claim. Shipped config at time of mapping:
`fusion=rrf lex-weight=n/a lex-norm=n/a closet-boost=0.00 rerank=on(pool=10,weight=0.50,norm=sigmoid) unit=memory evidence=lexical`.


## The correction this map produced

An earlier claim in the session — "`RERANK_POOL=10` is the real cap on the fetch" — is WRONG,
and the map is what caught it. Both knobs bind, at different stages:

- `candidateKFor(limit, …)` = `limit × 3` = **15** under the shipped `limit=5`. `RERANK_POOL`
  acts only as a FLOOR here (`if k < rerankPool { k = rerankPool }`), and 15 > 10, so it never
  raises the fetch at any `limit >= 4`. **The fetch width is set by `limit`.**
- `applyRerankWith` then does `pool := min(s.rerankPool, len(ranked))`, so only **10** of those
  15 candidates are cross-encoded. **The rerank width is set by `RERANK_POOL`.**

So raising `RERANK_POOL` alone cannot help — there are only 15 candidates to draw from — and
raising `limit` alone cannot help either, because the cross-encoder still sees 10. They have to
move together, which no single knob expresses.
